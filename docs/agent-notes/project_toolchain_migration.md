Goal: replace the proprietary MS-DOS build tools (run under kvikdos) with native open-source ones. Status as of 2026-06-17:

- **Assembler: DONE.** jwasm (`bin/jwasm-masm`) is the Makefile default (`ASM=wasm` toggles back to Open Watcom wasm). All `.ASM` assemble with 0 errors. See [[project_jwasm_make_invocation]] and [[project_jwasm_deep_set]].
- **Linker: DONE for pure-asm (Stage A).** `bin/wlink` (Open Watcom wlink wrapper, native, vendored in `watcom/bin/`) now links the 21 pure-assembly targets: boot, BIOS (IO.SYS), DOS kernel (MSDOS.SYS), all DEV drivers, and asm-only CMD utils (SHARE/IFSFUNC/NLSFUNC/ASSIGN/GRAFTABL/KEYB). The `$(WLINK)` make var selects it; `$(LINK)` (MS LINK) stays for the rest.
  - `bin/wlink` parses MS-LINK syntax (`@FILE.LNK` + inline `objs,exe,map,libs;`) -> wlink directives, then **canonicalizes wlink's 32-byte MZ header to 512 bytes** because the vintage MS EXE2BIN assumes MS LINK's 512-byte header and otherwise strips the wrong byte count (corrupting the image -- the image content is fine, only the header size mismatched).
  - Validated by byte-parity (strongest functional proof): wlink output BYTE-IDENTICAL to MS LINK for DRIVER, IO.SYS (13-module multi-segment), MSDOS.SYS, ANSI, VDISK, RAMDRIVE. Both paths use the same jwasm OBJs, so the linker is the only variable. wlink also resolved SHARE/IFSFUNC where MS LINK failed (L2029 unresolved OUT).

**Still proprietary (run via kvikdos):**
- **MS LINK** for C-containing targets: SMARTDRV, MEMM/EMM386, SELECT, and the C+asm CMD utilities (ATTRIB, FORMAT, CHKDSK, etc.). These reference the MS C 5.10 runtime (SLIBCE.LIB: `_printf`,`__chkstk`,`__acrtused`), which wlink can't resolve.
- **MS C 5.10 (`bin/cl` -> CL.EXE)** and **MS LIB (`bin/lib`)** and **MS EXE2BIN (`bin/exe2bin`)**.
- **Stage B (IN PROGRESS, 2026-06-17)** = migrate C compilation MS CL.EXE -> Open Watcom `wcc` + wlink the ~30 C-hybrids. Done so far:
- Vendored the OW 16-bit DOS runtime: `watcom/h` (110 headers, OS2/NT/Win pruned) + `watcom/lib286/dos` (clibs.lib etc.) from the OW 2.0 snapshot (downloaded; ddanila fork sources lacked it).
- `bin/wcc`: CL->wcc wrapper (`-AS`->`-ms`, `-Od`->`-od`, `-Zp`->`-zp1`, `-I`->`-i=`, `-Fo`->`-fo=`, plus forced `-ecc` cdecl + `-bt=dos` + `-i=watcom/h`).
- `bin/wlink`: appends `.obj`/`.lib` to extensionless names + `libpath watcom/lib286/dos`. Pure-asm still byte-identical (no regression).
- Pilot ATTRIB.C/ATTRIB.H compile clean under wcc (committed; still MS-CL-valid).

**Stage B is NOT a swap -- it's a C-runtime INTEGRATION project**, 3 layers per target:
1. Source compat: wcc errors (E1176) on size-incompatible pointer conversions MS C allowed. Fix pattern: widen generic pointer params to `void*` in the K&R definition (clears many call sites at once), then explicit near->far / exact-type casts at the rest. Plus `(BYTE)" "`->`(BYTE)' '` etc. ~7-25 fixes per file, ~30 files.
2. Startup reconciliation: utilities have a custom ASM entry (e.g. attriba.asm `end XCMAIN`) that conflicts with OW's `cstart` (E2030 multiple start addresses). Needs a startup strategy (force entry / suppress cstart / glue).
3. MS-runtime compat shim: SLIBCE extensions OW lacks -- e.g. `getpspbyte`/`putpspbyte` (PSP-byte access, used for the command tail at PSP:0x80). Must hand-write asm/C shims; each utility may use different SLIBCE extras. Also unprototyped clib calls (e.g. `exit` with no `<stdlib.h>`) emit cdecl `_exit` but OW's clib is `__watcall` -- include the OW header so its pragma fixes the convention.

This is a substantial multi-session effort; the infra (runtime + wrappers) is the reusable foundation. The 2 full-build link failures (SELECT.EXE, RESTORE.COM) are in this C-hybrid class.

**ATTRIB pilot (2026-06-17): links AND runs end-to-end** via wcc+wlink+OW clib. The proven per-target RECIPE:
1. Source-compat fixes (committed): widen generic K&R pointer params to `void*`; explicit near->far/exact-type casts at residual E1176 sites; `(BYTE)" "`->`(BYTE)' '`; `#include <stdlib.h>` + `exit()`->`exit(0)`. (All also MS-CL-valid.)
2. `getpspbyte`/`putpspbyte` shim (`pspbyte.c`, INT21h/62h) -- OW clib lacks these SLIBCE extras. Should become a shared compat module (currently in CMD/ATTRIB).
3. `bin/wcc -s` (no stack-check refs, since the custom XCMAIN entry doesn't provide OW's `__STK`).
4. Link: `wlink ... option start=XCMAIN libpath watcom/lib286/dos` -- forcing the asm entry avoids the OW `cstart` entry conflict (E2030) AND lets clib (printf/stdio) work without OW's cstart init (verified: printf outputs).

**ROOT CAUSE DIAGNOSED (2026-06-17) -- the core blocker:** wcc-built ATTRIB's `printf` output is silently lost; `/?` help prints nothing, and `setbuf(stdout,NULL)` doesn't help. Reason: **OW's clib stdio (`stdout` FILE table) is never initialized**, because the utilities' custom MS-style asm startup (attriba.asm `XCMAIN`) is the entry and bypasses OW's `cstart` runtime init (file/heap/_psp setup). So `printf`->uninitialized stdout->nothing. "Parse Error 9" only appeared because it goes through `Display_msg` (direct DOS INT21h write, NOT stdio). union REGS layout was a RED HERRING -- `_M_I86` IS defined, so OW's `union REGS` matches MS (di@10); my di-offset probe was bogus (non-constant array dim). So the parse interface is fine; the issue is purely uninitialized OW runtime.

**This is the central design decision for ALL C-hybrids:** OW clib needs OW's runtime init, which the custom XCMAIN entry doesn't do. Options:
  (a) Make XCMAIN call OW's runtime-init routines (need the OW init symbol, e.g. file-table init) before calling _inmain -- minimal but per-startup, requires knowing OW internals.
  (b) Drop the custom asm startups (XCMAIN) entirely; let OW's `cstart` be the entry (does full init incl. stdio), provide a standard `main()` that reads the PSP command tail (getpspbyte) and runs the utility's logic. Cleanest long-term, but reworks each utility's entry (and the per-utility int24/setup XCMAIN did).
  (c) Avoid OW stdio -- not feasible (utilities use printf).
**DEEPER DIAGNOSIS (continued 2026-06-17) -- option (a) hit a wall; (b) now recommended.** Tried option (a): added `call __InitRtns` (init) + `call __FiniRtns` (flush) + set OW heap globals (`__curbrk`,`__psp` via INT21h/62h) in attriba.asm before/after `_inmain`. Results:
- `__InitRtns` DOES run and DOES try to set up the FILE table -> progressed from "printf silently lost" to the OW runtime message **"Not enough memory to allocate file structures"**. So init runs; malloc fails.
- Root of malloc failure: **memory-layout impedance mismatch.** XCMAIN uses MS-C's layout (stack at TOP of the 64K segment, SP~0fff0); OW's near heap grows up from `_end` toward `__STACKLOW` and is bounded by `__curbrk`. Setting `__curbrk=0fffeh` (what cstart does, but cstart's stack layout differs) collides with XCMAIN's top-of-segment stack. Correct fix needs `__STACKLOW`/`__curbrk` set CONSISTENT with XCMAIN's actual stack position -- fiddly layout math.
- **BLOCKER for option (a): referencing OW symbols (`__InitRtns`,`__curbrk`,`__psp`) in attriba.asm BREAKS the MS build** (those aren't in SLIBCE). So the OW-init path can't live in the shared startup without conditional assembly / a separate OW-only startup file.

**=> Recommend option (b): drop the custom XCMAIN asm startups for the wcc build; let OW's `cstart` (in clibs.lib) be the entry -- it sets up segments/stack/heap/_psp AND inits stdio (`__InitRtns`) AND flushes on exit (`__FiniRtns`) correctly -- and provide a C `main()` that reads the PSP command tail (getpspbyte) and runs the utility logic.** This sidesteps both the layout-reconciliation and the MS-build-breakage. Per-utility entry rework, but mechanical once templated on ATTRIB.

**OPTION (b) IMPLEMENTED & WORKS (2026-06-17): the runtime-init blocker is SOLVED.** For ATTRIB, let OW's `cstart` be the entry (not XCMAIN); it inits stdio/heap correctly. Recipe (all committed, MS-build still works):

**PROGRESS (continued): three layers fixed, ATTRIB parses now.** Root causes were a cascade of MS-C-ABI assumptions wcc breaks:
1. `strcpy(fix_es_reg, NUL)` (NUL=0) = null-pointer read; MS C: DGROUP:0 is zero-guard (copies nothing + reloads ES=DS). wcc: DGROUP:0 nonzero -> overruns 1-byte fix_es_reg[] -> corrupted the command-tail buffer. FIX: `strcpy(fix_es_reg, "")` (16 sites; keeps MS ES-reload, safe under wcc). COMMITTED. Command tail now survives intact.
2. **`_PARSE.ASM` never set ES before `call sysparse`**; sysparse reads the parse control block at **ES:DI**. MS C kept ES=DS (via the fix_es_reg hack); wcc doesn't, and Get_DBCS_vector's `intdosx` left ES = the DBCS buffer segment -> sysparse read parmlist from wrong segment -> Parse Error 9. FIX: `push ds / pop es` before sysparse in _PARSE.ASM (each utility has its own _PARSE.ASM copy -- apply to all). COMMITTED. **Parser now matches correctly.**
Verified along the way: command tail read correct via `_psp`; union REGS matches MS (di@10); p_p1/p_px1 byte-dumped and CORRECT (p_minp=1,p_maxp=6, valid control ptrs).

- But the listing path keeps revealing MORE per-site MS-C-ABI/far-pointer issues. Exhaustively VERIFIED-CORRECT and ruled out: parser inputs, p_p1/p_px1 byte layout, union REGS (di@10), msg_str/msg_str1 contiguity (057d+0bh=0588), m_sublist layout (sizeof 11, sub_value@2/seg@4), SS==DS (0670==0670), substitution far pointers (valid). **SELECT wlink SIGSEGV ROOT-CAUSED + FIXED (2026-06-18).** Instrumented JWlink's `FindNode` (c/objnode.c) -> `FindNode bad SEG index=6 (num=3)`. Cause: SELECT sources use the `.ALPHA` directive (segment alphabetical ordering), and jwasm's `.ALPHA` SORTS the SEGDEF output (`CONST,DATA,SELECT,_BSS,_DATA,_TEXT`) but `SortSegments` (src/segment.c:1513) DELIBERATELY keeps each segment's definition-order `seg_idx` ("don't change indices, stored in fixup.frame_datum"). (`-zld`=no_opt_farcall suppresses just the COMENT: no crash but then E3011, fixups still inconsistent.) FIX (chosen source-side; `.ALPHA` is in 25 files, ALL in SELECT, nowhere else tree-wide): `.ALPHA`->`.SEQ` in those 25 files (MS-DOS jwasm-migration commit f9f7398). `.SEQ` = definition-order SEGDEFs, indices line up. VERIFIED: `bin/wlink "/noe @select.lnk"` now exits 1 (normal), not 245 (SIGSEGV); loads all 32 objects, reaches symbol resolution; only the pre-existing SLIBCE/SELECT.lib C-runtime deps remain -> SELECT is now the SAME C-hybrid (Stage B) class as other C utils, no longer a crash. Layout note: `.SEQ` orders segments sequentially not alphabetically; GROUP/class-driven for a normal .EXE so expected behavior-neutral, but smoke-test SELECT.EXE once the C-runtime side lands. Deeper jwasm engine fix (renumber seg_idx after sort + remap fixups, MASM-style) is a candidate to file vs ddanila/JWasm but NOT needed. So the 2 build link failures are now down to RESTORE.COM (still needs triage) + SELECT's C-runtime (Stage B).
